1. Overview

Everything here is a static site hosted on GitHub Pages straight from the repository root. There is no build step, no bundler, no framework and no backend of our own: the browser fetches plain HTML, CSS and JavaScript and talks to public APIs directly.

The BF6 dashboard in particular has no third-party JavaScript and no images at all — every visual is hand-drawn inline SVG or CSS. (The one exception in the whole repo is map.html, which loads Leaflet from unpkg.)

  • index.html — landing page, project cards, counter demo.
  • map.html + map.js — World Explorer: zoomable map, live weather (Open-Meteo), rain radar (RainViewer).
  • bf6.html + bf6.css + bf6.js — the BF6 player statistics dashboard, documented in the rest of this wiki.
  • wiki.html — this page.

4. Dashboard architecture

bf6.js is a single file, but it is not monolithic: banner comments divide it into layers that each do one job. Reading the banners top to bottom gives you the data path.

LayerBanner sectionsWhat lives there
Foundations CONFIG · HELPERS · FORMATTING · SMALL VISUALS Constants (API_BASE, limits), $()/el()/clear(), fmtInt/fmtPct/fmtDuration, small CSS-drawn visuals
Data in LOCAL CACHE / LIMITS · API LAYER The response cache and apiGet(): throttle, timeout, retry, cache
Shape NORMALISATION LAYER normaliseStats() and normaliseProfile() turn inconsistent API payloads into a stable shape the render layer can rely on
Data out RENDER LAYER · IDENTITY · OVERVIEW · CAREER · WEAPONS · CLASSES · … · SORTABLE TABLES One render*() function per panel. Each clears its own node, then fills it or shows an empty state
Diagrams INLINE SVG CHART · DIAGRAMS · RADAR CHART · WEAPON SCATTER · TRACKED PROGRESS · SESSION HISTORY The SVG primitives and the visuals catalogued in section 6
Orchestration CONTROLLER · LOADERS · INIT appState, URL and platform handling, loadPlayer() and friends, then init() which wires every listener

On the HTML side the rule is the same everywhere: a panel is .bf-panel containing a .bf-panel-head (heading plus an optional .bf-count caption) and a .bf-panel-body, which is the node a render function targets. Related panels sit in a .bf-chart-grid or a .bf-split.

The render contract: every render function owns one DOM node, calls clear(node) first, and when there is nothing to show appends a div.bf-muted with a plain-language message instead of leaving a hole or throwing. That is why around half of the profile fields arriving as null never produces a blank panel.

5. Workflows

5.1 What happens on page load

init() runs once at the bottom of bf6.js and does the same things in the same order every time:

  1. populatePlatforms() fills the platform select (PC, PSN, XBL).
  2. initPlatformSelect() defaults to PC and re-looks-up on change.
  3. Every "top N" toggle and the sortable table headers get their listeners.
  4. The search form, the Save button and the clear links get their listeners.
  5. renderRecent() and renderSaved() paint the stored chips, so the page is useful before any request leaves the browser.
  6. The URL is read; if it carries a name, loadPlayer() is called. A &vs= parameter additionally fills the optional Compare with field, so a shared head-to-head link reopens itself.
  7. loadSeason() and loadActivity() run — both are player-independent. They are deliberately started after loadPlayer(): every request joins one global throttle queue in the order it is first awaited, so calling them first held slots 1 and 2 and pushed the stats request back to slot 4 — roughly three seconds of queueing before any network time had even started.

This is the main flow of the whole page:

Profile and stats are requested together but the profile is optional: if it fails, loadPlayer() still receives null and renders the statistics with the identity panels showing empty states. A player always sees numbers rather than an error screen.

Comparing two players. Filling the optional Compare with field makes loadPlayer() schedule a second lookup after the first player has finished rendering, so a slow second name can never hold up the page the visitor actually asked for. Both players go through the same fetchStats() helper and therefore share the throttle queue, the normalisation and the "no such player" rule.

The comparison carries its own token and its own error surface. A mistyped second name is reported inside the head-to-head panel and changes nothing else: the first player's statistics are still valid and are still what the visitor came for. Starting a new search invalidates any comparison still in flight. Both platforms are separate dropdowns — the second defaults to the first but stops following as soon as the visitor picks one.

Volume is not skill. The table marks a leader only on the eight rows where higher is genuinely better. Kills, deaths, matches played and score carry a volume tag and are never crowned, because a player with three times the matches has three times the kills: highlighting them would reward playtime rather than performance. The same rule governs the per-class block, which is why it compares each player's share of their own kills per class and then K/D and KPM — the shares describe playstyle, the rates describe performance, and raw kills per class are never shown side by side because the player with more matches would win every row before performance entered into it. A dash in that table means the player has no record of that class at all, and a row containing a dash is never crowned. The overlay reuses the radar's own nine axes and its own ceilings, so the two shapes are directly comparable rather than two differently scaled polygons.

Concurrent lookups are serialised by a token. Every loadPlayer() increments lookupToken and keeps its own copy. The copy is re-checked after each await, and the catch and finally blocks only act when their copy is still the newest. Without it a slower, earlier search finishing last would repaint the page with the wrong player, and its finally would re-enable the search button while a newer lookup was still running. A lookup that passes four seconds also rewrites its button label to “Still loading…”, so a slow request never looks like a dead page.

What stays on screen when a lookup fails depends on the kind of error, because appState.showingPlayer tracks whose numbers are rendered and visible. The older appState.hasLoaded flag could not express this: it was written once on the first success and never cleared, so every later failure — including a 404 — took the “keep the old stats” path and left a previous player's numbers sitting under a “Player not found” banner.

FailureWhat the visitor seesWhy
notfound (404) The previous player's stats are hidden and showingPlayer is cleared. A 404 is a definitive answer about the name just typed. Someone else's numbers left under a “Player not found” banner read as if they belonged to that name.
timeout, network, server The previous player's stats stay, plus a #bfStaleNotice banner naming whose they are. These say nothing about the data already on screen, so wiping the page on a flaky connection would be worse. The banner removes the ambiguity.
any failure with nothing rendered Only the error status. There is no stale data to protect.

loadSessions() is no longer called from loadPlayer(): /manager/sessions/ carries no BF6 data, so it returned 404 on every lookup and simply burned a throttle slot that delayed the next search. Its panel markup remains in the page, hidden, in case that endpoint ever gains BF6 coverage.

5.3 Being polite to the API

All traffic goes to the public gametools.network API, so every request is funnelled through one function, apiGet(), which enforces four limits defined at the top of the file:

ConstantValuePurpose
THROTTLE_MS1 000At most one outbound request per second. Implemented as a promise chain rather than a timestamp check, so concurrent callers queue instead of colliding.
CACHE_TTL_MS10 minutesResponses are stored in localStorage keyed by the full URL and reused while fresh. The value mirrors the API's own cache-control: max-age=600.
REQUEST_TIMEOUT_MS12 000An AbortController cancels slow requests so the page never hangs on a spinner.
MAX_RETRIES1A single retry, and only for transient 5xx responses. 404 is not retried — it means the player does not exist.

The practical effect: re-running the same search within ten minutes is instant, and hammering the enter key cannot flood the API.

A 404 is confirmed, not trusted. One more quirk worth knowing about. The API intermittently answers 404 for players that demonstrably exist — it did so twice during testing, while /bf6/gameevents/ answered normally throughout, so the behaviour is specific to the player-stats lookup rather than a general outage. A lone 404 is destructive here, because it hides the page and tells the visitor that their player does not exist. So fetchStats() never believes one on its own: it waits, asks again, and only a second 404 is reported as an absence. Someone who mistypes a name waits about a second longer for the answer, which is a good trade for not lying to them.

The confirmation is scoped to /bf6/stats/ alone. /bf6/profile/ returns 404 as a matter of course and is already treated as optional, and the season and activity panels involve no player lookup at all, so neither would repay a second request. If the confirming attempt fails with a timeout rather than a 404, that propagates as a transient error instead — the absence was never established, so it is not asserted.

5.5 Sharing, and what the URL carries

After a lookup the URL becomes bf6.html?name=PlayerName&platform=pc via history.replaceState(), so the address bar or a bookmark always reloads exactly what you are looking at. Because replaceState is used rather than pushState, typing five names does not fill the back button with five history entries.

5.6 Errors and empty data

  • Unknown player — the API answers 404; the error banner names the platform it searched, because misspelled names are usually a platform mismatch.
  • Profile unavailable — treated as optional; stats still render.
  • Sessions empty — the panel hides itself instead of showing a zero.
  • Field is null — the panel shows a plain-language empty state. Many of the ~270 profile fields are null even for active players, so this is the normal path, not an edge case.

6.1 Donuts

renderDonut() draws the two ring charts. Each slice is a full <circle> whose coloured part is produced by stroke-dasharray — a dash as long as the slice's share of the circumference, followed by a gap as long as the rest — combined with stroke-dashoffset to start each slice where the previous one ended.

Why not arc paths? A single 100 % slice has no start and end angle, so it cannot be expressed as an SVG arc at all — the path collapses and nothing is drawn. Players whose XP is 100 % performance XP are common, so the dash technique is used because a circle with a full-length dash renders correctly.

Zero-valued slices are filtered out first, the centre text is a <text> element, and the legend beside it is ordinary HTML rather than SVG so long labels wrap.

6.2 Radar

Nine axes, each divided by its own realistic ceiling and clamped to 0–100 % with clampScore(), then plotted around a circle and joined into a filled <polygon>. Four background rings (25 / 50 / 75 / 100 %) and the axis spokes are drawn first, so the shape always reads against a scale.

AxisPlotted at 100 %Why that ceiling
K/D3A strong ratio; above this is rare
Kills/min4Sprint tempo, not turtling
Damage/min800High but reachable on a good round
Accuracy50 %Sustained fire rarely exceeds it
Headshot rate70 %Sniper-heavy players approach it

Points/min500Derived: lifetime score ÷ minutes played

The ceilings are a display heuristic invented here, not a scale the game defines. They exist so that a 25 % accuracy — genuinely good — does not render as a flat edge against a naive 0–100 axis. That also makes the geometry ambiguous on its own: a vertex at 60 % of the way out means something completely different on Accuracy than it does on Damage/min. So the real value is printed on the chart itself, directly under each axis label, and every legend row shows both the real number and the normalised score. Hovering a vertex reports all three plus the ceiling it was measured against, which is also how a saturated axis reads — a player at 3.12 revives per match scores exactly the same 100/100 as one at 3.00, and only the printed value shows the difference. If fewer than three axes have data the chart declines to draw and says so.

6.3 Bars

Bar panels are plain HTML, not SVG, and come in two flavours. renderSharePanel(node, entries, formatter) draws a track with an inner fill whose width is that entry's share of the total, plus the formatted value — used for class time, mode time and weapon-class kills, where "how much of my total" is the interesting question. renderModeCompare() instead draws three separate metrics (K/D, win rate, accuracy) per game mode, each normalised against the best mode, so you can see at a glance that you are a Breakthrough player who is mediocre at Domination.

6.4 Scatter

renderWeaponScatter() plots one dot per weapon: x = kills, y = accuracy, and the radius encodes a third dimension — shots fired — as 3 + 7 × √(shotsFired / maxShots). Square root, not linear, because area should grow with the value; a linear radius would make well-used weapons look absurdly large. Both axes scale to the player's own maximum, and weapons with no kills, no shots or zero accuracy are dropped, as are players with fewer than two usable weapons.

6.5 Lines

Two line charts, and it matters which is which. The activity chart comes from /bf6/statusarray/ and is genuinely live: hourly counts of players in the game across the last week, shared by everyone. The tracked progress chart comes from your own bf6.snapshots.v1 store and is a line of your K/D, accuracy, win rate or kills/min (chosen with the toggle above the chart) recorded each time you run a lookup.

There is no match history anywhere. The API exposes no per-match list — /bf6/history/, /bf6/battlelog/ and /manager/sessions/ all return 404 — so the trend chart cannot show your last thirty games. What is derivable is a difference of totals: every figure the API returns is a lifetime cumulative counter, so subtracting one snapshot from the next gives exactly what was played in between. That is what the session log (renderSessionLog) does. Both the trend chart and the session log start at your first visit to this dashboard and only ever contain lookups made from this browser. Their edges are when you pressed Search, not when the game thought a round ended.

7. Conventions and gotchas

  • No images, ever. There is not one <img> tag in the repo — no game artwork to infringe, nothing to compress, nothing to lazy-load. Anything that looks like a graphic is CSS or inline SVG.
  • vector-effect: non-scaling-stroke goes on every SVG line and polygon. Without it, strokes scale with the viewBox and hairlines become fat ropes on wide panels.
  • Empty states are the default path. Never render a bare 0 or null; show a div.bf-muted sentence explaining what is missing.
  • Names are exact and case-sensitive. The API does not fuzzy-match, which is why the label says "exact match" and recent/saved chips exist at all.
  • API quirks are mirrored, not corrected — the request parameter is seperation= (one p), and the profile fields really are spelled devidedDamage and devidedAssists. "Fixing" either silently breaks the panel.
  • XP is an array with a single interesting element, so it is read as d.XP[0].
  • Charts refuse, they don't guess. The radar needs three axes, the scatter needs two weapons; below that they render a sentence instead of a misleading shape.
  • Every chart carries an "i" badge. A span.bf-info in the .bf-panel-head explains the figure in one sentence through its title attribute. Native tooltips are deliberate: .bf-panel sets overflow: hidden, which would clip a CSS-positioned tooltip.
  • perGamemode is a partial sample. It only appears when seperation=true is sent, and its per-mode totals do not add up to the career totals. On a test account it covered 78 of 147 matches and omitted three modes the player had played. Anything drawn from it must say so out loud. By contrast maps, weapons and the core counters do reconcile, so those can be presented as complete.
  • Bump the asset version on every deploy. The stylesheets and scripts are referenced with a ?v= query string because GitHub Pages serves every file with Cache-Control: max-age=600. Without the bump a returning visitor can keep an old script for ten minutes while the new markup has already arrived, which is how panels silently end up empty. Raise the number in every page that references a file you changed. As a second line of defence every render function returns early when its node is absent, so a stale document degrades to a missing panel rather than a blank one.

7.1 Adding a panel

  1. Add the markup in bf6.html: .bf-panel with a .bf-panel-head and an empty .bf-panel-body carrying a unique id.
  2. If it needs new data, extend normaliseStats() or normaliseProfile() — never read raw API fields inside a render function.
  3. Write the render*() function: clear the node, handle the empty case first, then fill.
  4. Call it from loadPlayer(), so it runs on every lookup.
  5. Add styles to bf6.css using the existing --bf-* variables.
  6. Cross-check: every getElementById target exists in the HTML, and every new class has a rule.

8. Running locally

Serve the repository root over HTTP rather than opening files directly:

cd d:\Dokumente\Github_Repro\test_env
python -m http.server 8500
# then open http://localhost:8500/bf6.html

A file:// origin is treated as opaque by browsers, so fetch() to the API and same-origin requests behave inconsistently. Any static server works — python -m http.server, VS Code's Live Server, npx serve.

8.1 Branches and the beta preview

A switch in the nav of the BF6 dashboard moves between the stable site and the beta one without leaving the page you are reading. It sits on that page alone on purpose: index.html, map.html and this wiki are byte-identical in both channels, so a switch on any of them would only reload the page you are already on. Three branches sit behind it:

BranchLive atRole
main / Stable. Every commit here is on the public site.
beta /beta/ Candidate builds, reached through the switch on the BF6 page. The last place something is looked at before it reaches the public site.
dev never published Free-for-all development. Because it is not deployed, it is allowed to be broken.

Promotion runs dev → beta → main, one explicit merge at a time. Nothing moves between branches on its own.

GitHub Pages on the free plan serves exactly one site per repository, so both live versions are produced by .github/workflows/pages.yml, which assembles a composite tree — main into the root and beta into /beta/ — and hands it to actions/deploy-pages. The beta checkout is marked continue-on-error, so a repository without a beta branch yet still deploys the stable site alone instead of failing the run.

This only works because every link in the site is relative. There is no url(/…) in the CSS, no href="/…", no ES-module import and no location.pathname used for assets anywhere in the repository, so the identical files work unchanged when served from a subdirectory. The switch derives its own target from the path: turned on under /beta/ it points up to ../…, anywhere else it points down to beta/….

The switch is a real <input type="checkbox"> inside a <label>, so it is keyboard operable and announced correctly with no ARIA. Its state reflects the channel you are actually on rather than the one you would move to. A single URL can only ever serve one build, so flipping it navigates instead of swapping content in place — and it starts hidden so that without JavaScript it never appears rather than linking somewhere wrong.

Deploying by hand. Pushing to main or beta deploys automatically, and the workflow also carries a manual Run workflow trigger — the quickest way to force a redeploy without committing anything. Two repository settings have to be right before either works, and they mask each other:

  1. Settings → Pages → Source = GitHub Actions. While this still says Deploy from a branch, branch deployments keep winning and nothing from this workflow is ever served, however green it goes.
  2. Settings → Environments → github-pages → Deployment branches and tags: allow beta. actions/deploy-pages deploys through the github-pages environment, GitHub creates that environment protected, and by default it permits only the Pages source branch. This is the one that blocks a beta push.

The order matters, and getting it wrong is genuinely confusing. Environment protection rules take precedence over the source-branch rule, so a run from beta is refused at the second setting long before it ever reaches the first — which makes the source setting look innocent. Fix the environment first and the run goes green without changing a single byte of the live site, because the deployment it would have replaced was never live anyway. Both have to be right.

What the rejection looks like. It happens before the job starts: the deploy job reports failure with an empty steps array and no runner, while build sits there green having uploaded a perfectly good artifact. Nothing in the workflow can catch it, because nothing in the workflow runs — so the build job emits its own warning annotation on every beta push, naming the setting to change. A run from main succeeds throughout, which makes the whole thing look intermittent rather than systematic.
